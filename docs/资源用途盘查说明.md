# CakeHome 美术资源用途盘查说明

> 2026-09-12 编写。目的：**换图前先搞清楚每张图在游戏里是什么、干什么、有什么约束**。
>
> 盘查方法（不靠文件名猜）：
> ① 静态反查 — prefab/scene 的 GUID 引用（`Tools/art_usage_map.py`）
> ② 运行时反查 — 在跑着的游戏里枚举真实 SpriteRenderer / Image（`Tools/probe_usage.py`）
> ③ 代码反查 — 读控制器逻辑确认机制（`LevelController` / `TileBehavior` / `TileEffect`）
> ④ 结构反查 — 读 `.meta` 的 `spriteBorder` 判断是否九宫格（`Tools/art_dossier.py`）

## 一、三消棋盘：两层结构（最关键的发现）

实测运行时，棋盘的每个格子是**两个 SpriteRenderer 叠加**：

```
Tile C1T4  (TileBehavior)
├── Back = tile_background      ← 棋盘格底座，54 个格子共用这一张
└── Icon = tile_c1_t4           ← 该格的棋子图案（主题1·4级）
```

**证据**（Unity 运行时查询）：
```
Tile_Tile C1T4_3 e5: Back=tile_background  Icon=tile_c1_t4
Tile_Tile C3T5_14 e5: Back=tile_background  Icon=tile_c3_t5
```

### 命名规则
`tile_c{集合}_t{等级}`

| 维度 | 含义 | 取值 |
|---|---|---|
| `c` | **棋子主题集合**（collectionID） | c1 甜点 / c2 咖啡 / c3 糖果 |
| `t` | **棋子等级** | t1~t5，共 5 级 |

### 玩法意义
- `LevelDatabase.AvailableForLevel(levelId)` 按 `availableFromLevel` **逐关解锁**主题
- `LevelData.ElementsPerLevel` 决定该关**随机启用几种**棋子
- 玩家**完全依赖图案**判断「能不能消」「是几级」

> 🔴 **结论：`tile_cX_tY` 是玩法信息载体，图案不可更改。**
> 把 5 个等级画成同一形状 = 玩家无法辨别等级 = 游戏不可玩。
> （实测教训：重绘后 15 张全变成同款空框）

### 底图约束
- `tile_background` 是**所有格共用的底**，图案简单（纯色圆角方形）
- 它**不是**装饰，而是「空格 vs 有子」的视觉基准
- 可换色，但**中心必须留白**（因为上面要叠 Icon）

## 二、特殊瓦片（障碍机制）

`Gameplay/Tiles/Special` 6 张，每张绑定一个效果类：

| 资源 | 效果类 | 机制 |
|---|---|---|
| `tile_crate` | `CrateTileEffect` | 箱子：覆盖图标（`iconSpriteRenderer.enabled=false`），需多次消除打开 |
| `tile_ice_1~3` | `IceTileEffect` | 冰：**3 个阶段**（`stageSprites[0..2]`），逐级破除 |
| `tile_link` | `LinkedTileEffect` | 锁链：连接两个格子，**会旋转**（`Quaternion.Euler(0,0,angle)`），按两点中点定位 |
| `tile_unknown` | `UnknownTileEffect` | 未知：未探明状态的遮罩 |

**约束**：
- `tile_link` **必须适合任意角度旋转** → 图形要中心对称或可旋转
- `tile_ice_1~3` 是**递进三态**（完整→裂纹→破碎），顺序不能乱
- 这些**形状本身就是机制提示**，换成别的形状玩家看不出是什么障碍

> 🔴 结论：形状与阶段序不可改。

## 三、UI 九宫格（19+8 张）

实测运行时 **195 个 Image 使用 `Image.Type.Sliced`**。

### 什么是 Sliced
`.meta` 里的 `spriteBorder` 把图切成 9 块：
```
┌─────┬───────────┬─────┐
│ 角  │  上边(拉伸)│ 角  │  ← 角不拉伸、边单轴拉伸
├─────┼───────────┼─────┤
│左边 │  中心(双轴)│右边 │
├─────┼───────────┼─────┤
│ 角  │  下边(拉伸)│ 角  │
└─────┴───────────┴─────┘
```

### 关键约束
| 资源 | 尺寸 | spriteBorder | 边框占比 |
|---|---|---|---|
| `btn_gray/green/orange/purple` | 156×216 | (58,76,50,58) | **37% / 27%** |
| `ui_button_*` (5张) | 1024² | (452,353,452,353) | **44% / 34%** |
| `panel_*` | 512² | (100,120,100,100) | 20% |
| `ui_panel_white` 等 | 512² | (80,80,80,80) | 16% |

**边框占比高达 37~44%**，意味着可拉伸区很小 —— 边缘像素一旦变化，拉伸必然撕裂。

> 🔴 结论：**九宫格图不能重绘**。
> AI 生成的是「一个有装饰的完整按钮」，中心有内容 → 拉伸后必然错乱。
> （实测 3 轮：模型把 "uniform center" 理解成「画个黑洞」或产出直角矩形）
> ✅ 唯一安全做法：**保留原几何，只做色调调整**（已实现于 `Tools/reskin_9slice.py`）

## 四、TMP 字体字符图集

`Fonts/FredokaOne 50`（4张）、`Fonts/FredokaOne 120`（2张）

- 这些是 **TextMeshPro 的字符位图图集**（Texture/Glow/Outline/Outline Light）
- 图里每个小格是一个字符的描边/发光/阴影层
- Unity 按字符坐标采样，**图里是什么字，UI 上就显示什么字**

> 🔴 结论：**不可重绘**。重绘 = 字符位图丢失 = 文字全显示不出来。
> （实测教训：被模型画成了「裱花相框」）

**另注**：项目还有已知问题 —— `FredokaOne 50` 无 CJK 字形也无 fallback，中文 UI 显示为空格。

## 五、大地图（三消关卡地图）

`Map` 7 张：`map_c0~c4`（四季地块）+ `map_level`（关卡按钮）+ `cloud`

### 实测用途
```
map_c0 ~ c4  → 世界地图的五个区域地块
map_level    → 关卡节点按钮（运行时 40 个实例）
cloud        → 装饰云（运行时 4 个实例）
```

### 四季主题（从原图采样）
| 地块 | 主色 | 季节 |
|---|---|---|
| `map_c1` | 黄绿 + 亮绿 | 春·草地 |
| `map_c2` | 金黄 + 米白 + 橙棕 | 秋·麦田 |
| `map_c3` | 雪白 + 淡粉 | 冬·雪原 |
| `map_c4` | 嫩绿 + 米黄 + 粉 | 春末·樱花 |
| `map_c0` | 亮绿 | 起始草原 |

### 约束
- 尺寸 **2200×2400**（超大）
- 需要**俯视平面地形**：大面积地形色 + 蜿蜒浅色路径
- 地块需能**拼合成一张大地图**

> 🔴 结论：**不能画成「立体装饰物」**。
> （实测教训：被画成立体蛋糕塔，地形色与路径全失，无法铺成地图）

## 六、门店场景（Zone 1）

`Scene/Zone1` 22 张：`z1_{house,table,bush,fence,fountain}_{1..4}`

### 机制约束
- 受 **`buildingId` 槽位**约束，与玩家**存档绑定**
- 每个物件 4 档升级，**升级成本固定**（Zone1 565 / Zone2 3955 / Zone3 9605）
- Prefab `Zone 1.prefab` 直接 GUID 引用这 20 张图

**5 槽位映射**（已有设计，见 KNOWLEDGE.md）：
| 槽位 | 原物件 | 目标改造 |
|---|---|---|
| building_1 | house | 后墙左高柜 |
| building_2 | fountain | 前景玻璃柜 |
| building_3 | table | 圆桌餐椅 |
| building_4 | fence | 右高柜 |
| building_5 | bush | 三层点心塔 |

> 🔴 结论：**换内容会破坏存档语义**。
> 若要从「庭院」改成「店内」，必须整套换（背景+5物件×4档），
> 且 **`buildingId` / 存档 / 成本逻辑完全不变**。
> 目前店内素材已生成（4 背景 + 20 物件），但**尚未接入**。

## 七、可安全替换的资源类型

综合以上，只有这几类**换掉不影响功能与辨识**：

| 类型 | 例 | 理由 |
|---|---|---|
| **纯背景板** | `Scene/Backgrounds` back_1~4 | 装饰性，下方留白区是唯一约束 |
| **特效贴图** | `Fx` 星星/火花/雾 | 叠加层，只需保持亮部透明过渡 |
| **宝箱外观** | `Gameplay/Chests` | 装饰性，但**必须保持闭合态**与档位递进 |
| **角色立绘** | `Gameplay/Characters` | 装饰性，需保持同一角色形象一致 |
| **货币/内容图标** | `UI/Icons` 里的 coin/gem/energy | 有实体，但**语义色需保留**（能量=蓝、宝石=紫） |
| **对话 UI 装饰** | `Dialog` 气泡/头框 | 装饰性，遮罩类除外 |

## 九、本次事故复盘

| 事故 | 错误做法 | 实际用途 | 损失 |
|---|---|---|---|
| `Gameplay/Tiles` | 按「棋盘格底图」重绘成空框 | 是**棋子图案**（三主题×五级） | 23 张 |
| `Map` | 按「地图装饰元素」重绘 | 是**俯视四季地形地块** | 7 张 |
| `Fonts` | 按「装饰文字贴图」重绘 | 是 **TMP 字符图集** | 6 张 |
| `UI/Common` | 按「UI 元素」重绘 | 含**九宫格**，边缘像素锁死 | 34 张 |

**共同根因**：按**文件名 + 视觉相似度**推测用途，未查证**在游戏中的实际角色**。

**正确流程**（本文档确立）：
```
① 运行时查它出现在哪  → ② 读代码查它干什么用  → ③ 读 meta 查结构约束
→ ④ 判定风险等级 → ⑤ 写说明确认 → ⑥ 才动手
```
